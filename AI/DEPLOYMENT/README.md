# Deployment Builder — AI/DEPLOYMENT

Purpose

This folder documents the Deployment Builder that prepares the repository output for Google Apps Script (clasp). The repo retains a professional, nested folder layout; the Deployment Builder produces a flattened, deterministic, uniquely-named build folder that clasp can safely push.

Key goals

- Preserve the Git repo architecture (do not rename or edit source files).
- Produce a deterministic build/ directory containing only deployable files with globally-unique names.
- Rewrite HtmlService includes (<?!= include('...') ?>) to reference the generated filenames.
- Provide validation, reporting, rollback capability and a one-command workflow for build → validate → clasp push.

Contents

- Tools/DeploymentBuilder.js — Node script that performs the build pipeline
- Tools/DeploymentValidator.js — lightweight validator for build output and includes
- Tools/DeploymentConfig.json — configuration (paths, ignores, file types)
- AI/DEPLOYMENT/DEPLOYMENT_ARCHITECTURE.md — architecture notes
- AI/DEPLOYMENT/DEPLOYMENT_WORKFLOW.md — developer workflow and commands
- AI/DEPLOYMENT/DEPLOYMENT_REPORT_TEMPLATE.md — template for final report generated by builder

How to use

1. From repository root run (Node required):
   node Tools/Build.js --config Tools/DeploymentConfig.json

2. Full deploy (build + push + versioning):
   node Tools/Deploy.js --config Tools/DeploymentConfig.json --deploy

3. Validate build (optional but recommended):
   node Tools/DeploymentValidator.js --config Tools/DeploymentConfig.json

Notes

- The builder never modifies source files.
- The repository .clasp.json remains authoritative; Deploy.js reads it and generates build/.clasp.json for the deploy workspace.
- The build/ directory is the only folder pushed to Apps Script. Source files are never uploaded.
- Running the builder twice produces identical build/ output if sources did not change.
- Review AI/DEPLOYMENT/DEPLOYMENT_WORKFLOW.md for detailed lifecycle and flags.

Configuration schema (Tools/DeploymentConfig.json)

The builder is configuration-driven. Example config (Tools/DeploymentConfig.json):

{
  "sourceRoots": [ ".", "Components", "Modules" ],
  "ignoreDirs": [ ".git", "node_modules", "AI", "build", "dist", "dist_versions", "coverage" ],
  "extensions": [ ".html", ".js", ".gs" ],
  "buildDir": "build",
  "logFile": "build/deployment_log.txt",
  "reportFile": "AI/DEPLOYMENT/DEPLOYMENT_REPORT.md"
}

Key fields

- sourceRoots: array of folders to scan. Use "." for repository root. The builder will scan these directories recursively.
- ignoreDirs: folder names to skip during scanning (recommended: .git, node_modules, AI, build, dist, dist_versions, coverage).
- extensions: file extensions to include in the build (default: .html, .js, .gs). Backwards-compatible key includeExtensions is supported.
- buildDir: destination folder for generated deployable files.
- logFile: path to write build logs (relative to repo root).
- reportFile: path to write the deployment report.

Best practices

- Keep ignoreDirs up-to-date (add any temporary or generated folders to avoid scanning them).
- Avoid adding business-specific files to the builder — it is intentionally generic.
- Use the validator in local dev before clasp push.

Backward compatibility

- If a config uses includeExtensions (older name) it will be mapped to extensions automatically.
- sourceRoots supports "." which maps to repo root and is compatible with prior empty-string configuration.
